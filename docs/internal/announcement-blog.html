Introducing kars — the Agent Reference Stack for Kubernetes

By Pal Lakatos-Toth · Maintainer, kars launchenterprisesecuritykubernetesai-agents

Today I'm publicly introducing kars — a Kubernetes-native runtime for AI agents that takes the position that running agents in an enterprise is fundamentally different from running stateless microservices, and that the existing stack does not yet reflect that. kars is open source under the MIT license, runs on Azure Kubernetes Service today, and integrates natively with the Microsoft Agent Governance Toolkit (AGT) — the governance engine kars consumes through four provider traits, with selected gap-closing features upstreamed back to AGT itself.

TL;DR

  • What: a Kubernetes operator + per-agent inference router + E2E-encrypted inter-agent mesh that lets you run AI agents from any of eight first-class frameworks with one consistent security, governance, and audit posture.
  • Why now: Gartner predicts 40 % of agentic-AI projects will be cancelled by end of 2027; the dominant failure mode is not model quality — it's governance, isolation, and the absence of an operator-grade audit trail.
  • Position: per-pod, kernel-confined trust boundary around every agent. Default-deny egress at the kernel by UID. Zero Azure credentials reachable from the agent process. Inter-agent traffic end-to-end encrypted with the Signal Protocol — the relay sees only ciphertext.
  • Consumes: AGT for policy evaluation, mesh primitives, audit chain, trust scoring, behaviour monitoring, and signing — never re-implemented. See AGT Boundary for the exact split. kars has upstreamed gap-closing features back to AGT in PR #2090, #2659, and #2719.
  • Confidential by opt-in: a single field — spec.isolation: confidential — schedules the sandbox on AKS Pod Sandboxing (Kata + AMD SEV-SNP). VM-level isolation per pod, separate kernel per workload.
  • Status: v0.1.0 — 8 runtime adapters shipping, 9 workload CRDs reconciled, 6 end-to-end use cases exercised by CI, 9/9 security layers validated on both AKS and kind.
  • Honest scope: if you have one agent, one team, and no adversarial-code threat model, kars is overkill. The crossover is around two teams, multi-runtime, or a regulator who has heard "prompt injection" before.
  • Source & docs: github.com/Azure/kars · documentation · MIT license · contributions welcome.

What ships today, and what it gets you

Below is the current capability surface — what v0.1.0 actually enforces in a running cluster today, what each capability is worth in operational terms, and where the gaps still are. The full enforcement matrix lives in docs/maturity.md.

① The agent process never sees an Azure credential. Workload Identity / IMDS broker (anonymous mode) or per-sandbox Microsoft Entra Agent ID via auth-sidecar (production mode, --mesh-trust=entra) lives in the inference router (UID 1001); the agent (UID 1000) is iptables-blocked from IMDS at the kernel. Prompt injection has nothing to exfiltrate. Per-scope token caching and refresh shipped. Status: enforced today.
② Kernel-confined, default-deny egress per sandbox. UID-based iptables egress guard, Kubernetes NetworkPolicy default-deny, router L7 allowlist on every outbound CONNECT, time-boxed EgressApproval exceptions, auto-refreshing OISD + URLhaus blocklist. Status: enforced today.
③ Hardened sandbox shape: read-only rootfs, drop-ALL caps, custom seccomp, Landlock. DaemonSet-installed kars-strict seccomp profile blocks mount, ptrace, bpf, unshare. Optional Kata + AMD SEV-SNP confidential-VM isolation via spec.isolation: confidential. Status: enforced today.
④ Native governance via AGT — not reimplemented. Policy evaluation, hash-chained audit, per-peer trust scoring, burst/failure behaviour detection, and per-identity rate limiting all consumed from AGT through four provider traits. We upstreamed connect-frame JWT verification, per-agent session counters, and the registry-verify endpoint to AGT (microsoft/agent-governance-toolkit#2719). Status: enforced today.
⑤ End-to-end encrypted inter-agent messaging the relay cannot decrypt. Signal Protocol (X3DH + Double Ratchet) via the AGT-Rust-SDK agentmesh crate. The router only WebSocket-bridges opaque ciphertext. Cross-runtime conversation (e.g. Hermes ↔ OpenClaw) is production-tested on AKS and kind. Status: enforced today.
⑥ Multi-runtime hosting — eight first-class adapters on one operator. OpenClaw, Hermes, OpenAI Agents (Python), Microsoft Agent Framework (Python), LangGraph (Python and TypeScript), Anthropic Claude Agent SDK, Pydantic-AI — plus a documented BYO contract with strict-mode admission gating. Same router, same governance, same audit chain for every runtime. Status: shipping today.
⑦ Operator-grade UX: CLI, TUI, GitOps, supply chain. kars up / add / dev / connect / handoff / mesh / migrate / convert / attest; the kars operator TUI; cosign keyless OIDC image signatures and SPDX-JSON SBOM per image; Trivy + cargo-deny + RustSec advisory audit run in CI on every dependency-touching PR. Status: shipping today.

Six end-to-end use cases are shipping and exercised by CI: kars-native OpenClaw on AKS, any-OpenClaw → kars cloud offload, kars ↔ kars mesh, multi-runtime hosting, public A2A federation across organisations (with mTLS-pinned subject), and migration from kagent or sigs/agent-sandbox. Why I built this — five things I think the industry has gotten wrong

I have spent the last year talking to enterprise platform teams, CISOs, and AI leads about what is actually blocking agentic deployments. Five patterns came up repeatedly. Each one is an assumption kars rejects.

1. "An agent is just a stateless microservice with an LLM in it."

It is not. An agent's code is partially generated at runtime by an untrusted source — the model output, the tool response, the previous turn's context, an MCP server you do not control. The threat model is closer to "running customer-submitted code" than to "running a service you wrote." The implication is that the agent process must hold no secrets, must have no ambient network reach, and must be isolated at the kernel level — not just at the network policy level. That is the entire reason kars's sandbox is built the way it is.

2. "Governance is something you bolt on later."

Governance is the workload. Without policy evaluation, audit, trust scoring, and rate-limiting present from the first commit, the agent platform becomes unrenovatable. The right move is to consume a real governance engine — for us that is AGT — through stable provider seams from day one. kars's AGT boundary document says explicitly what kars never builds: no custom Signal primitives, no standalone audit chain, no parallel trust engine, no separate rate-limit bucket, no key custody. Any overlap is treated as a bug to resolve, not a feature to negotiate.

3. "Inter-agent communication is the same problem as service-to-service."

It is not. Service-to-service can rely on the cluster network as the trust boundary, because services know their own threat model. Agents do not — the agent's code can be steered by an attacker through prompt injection. So the message bus has to remove the broker from the trust set. kars uses AGT's end-to-end Signal-Protocol encrypted mesh where the relay routes ciphertext and cannot read message contents. The structural difference from a service mesh is the same as the difference between an HTTPS proxy and PGP-encrypted email. Both are valid. They are not equivalent.

4. "Multi-runtime is a transitional problem."

I do not believe it is. The framework landscape — OpenClaw, Hermes, MAF, LangChain, LangGraph, CrewAI, OpenAI Agents SDK, Anthropic Claude Agent SDK, Pydantic-AI — is converging on shared standards (MCP, A2A, AGT adapters), not on a single winning framework. kars ships eight first-class runtime adapters today and treats multi-runtime as the steady state. The same router, the same governance profile, the same audit chain apply across all of them; switching runtime is a one-field change in KarsSandbox.spec.runtime.kind.

5. "Sidecars are dead."

The Istio ambient-mode discussion has confused this point. For cluster-wide service-mesh traffic management, ambient is often the right choice. For a per-pod, kernel-confined, adversarial-trust boundary around one specific agent, a sidecar is structurally the right shape. KEP-753 made native sidecar containers a first-class K8s primitive in v1.29 — this is the building block kars uses. The relevant question is not "sidecar yes/no" — it's "where does the trust boundary belong?" The answer for agent code is "as close to the agent as possible, in the kernel."

CISO / Security Lead

The security model in one page.

  • Zero Azure credentials in the agent process. The agent container (UID 1000) has no model API key, no cloud SDK token, no MCP secret. The per-pod inference router (UID 1001) holds them, authenticates with a per-sandbox Microsoft Entra Agent ID via the auth-sidecar (production mode, --mesh-trust=entra) — or cluster-wide Workload Identity (anonymous mode) — and exposes only the call surface, never the credential. Prompt injection has nothing to exfiltrate.
  • Kernel-level egress confinement. An iptables init container restricts UID 1000 to localhost and DNS. The agent process literally cannot open a socket to the public internet. All egress flows through UID 1001, which applies an L7 allowlist with an auto-refreshing malicious-domain blocklist (OISD + URLhaus) refreshed daily by a CI cron job.
  • Per-pod blast radius. One sandbox compromise contains to one Kubernetes namespace, one NetworkPolicy, one per-sandbox Entra Agent ID, one token budget. There is no cluster-wide single point of compromise.
  • End-to-end encrypted inter-agent messaging. Signal Protocol (X3DH + Double Ratchet) via the AGT Rust SDK agentmesh = "4.0.0" crate. The relay routes ciphertext and cannot decrypt. Forward secrecy per message.
  • Hardened container shape. Read-only rootfs, drop-ALL capabilities, non-root, no privilege escalation, custom kars-strict seccomp profile (175 allowed / 41 explicit-deny syscalls, blocking mount / ptrace / bpf / unshare), Landlock. Pod Sandboxing (Kata + AMD SEV-SNP) is one field away — see the spotlight below.
  • Hash-chained audit with tamper detection via AGT's AuditLogger; cosign keyless OIDC image signatures and SPDX-JSON SBOM per image; Trivy + cargo-deny + RustSec advisory audit run in CI on every dependency-touching PR. Threat model: STRIDE walkthrough; red-team scenarios: red-team playbook; control mapping: NIST SP 800-53 + CIS Kubernetes; enforcement matrix: maturity page (the single source of truth for enforced vs reconciler-only vs roadmap).
AI / Agentic AI Lead

Why this is interesting if you actually build agents. Most agentic stacks treat the agent as a single, monolithic process. Real agentic workloads spawn sub-agents, hand off tasks, call MCP tools, write to memory, and operate across organisational boundaries. kars takes each of those seriously. A minimal KarsSandbox looks like this:

apiVersion: kars.azure.com/v1alpha1
kind: KarsSandbox
metadata:
  name: research-bot
spec:
  runtime:
    kind: OpenClaw         # or Hermes, MAF, LangGraph, Anthropic, …
  model:
    provider: Foundry
    deployment: gpt-4o
  isolation: enhanced      # or 'confidential' → Kata + SEV-SNP
  egress:
    allowedEndpoints:
      - https://api.github.com
  tokenBudget:
    perRequestTokens: 8000
    perDayTokens: 1000000
  • Sub-agent spawn is governed. When an OpenClaw agent invokes kars_spawn or kars_handoff_request/kars_handoff_confirm, the child gets its own sandbox, its own policy bundle, its own token budget, and its own AGT trust score. Not a thread in the parent process.
  • Per-agent policy via AGT PolicyEngine. Hot-reloaded YAML rules gating exec / fetch / spawn / mesh send. Different agents can run with different policy bundles on the same cluster without sharing a control plane.
  • AgentMesh, not just A2A. Agents from different runtimes — OpenClaw, Hermes, MAF, LangGraph — talk to each other on a shared, end-to-end-encrypted mesh today. Cross-runtime Hermes ↔ OpenClaw conversation is exercised by the interop harness on kind on every push, and has been demonstrated on AKS (manual Entra RBAC provisioning required for new sandboxes). For cross-organisation flows, a public A2A gateway with mTLS-pinned subject is shipping (ADR 0001).
  • Memory governance. KarsMemory CRD bounds memory writes against per-agent policy. Foundry Memory Store today.
  • Agent evaluation in-cluster. KarsEval CRD replays a signed attack corpus against a sandbox and writes outcomes to the audit chain (operator guide).
  • Multi-framework adoption path. If you have invested in MAF, LangGraph, OpenAI Agents SDK, Anthropic Claude Agent SDK, Pydantic-AI, or Hermes (20+ messaging channels, 18+ inference providers, 70+ built-in tools, native MCP client out of the box), your existing agents run unchanged. The adapter wires your framework to the kars sandbox shape — you do not rewrite your agents to adopt kars.
  • Migration from upstream schemas. kars convert translates sigs/agent-sandbox resources; kars migrate from-kagent translates kagent CRs. Both target KarsSandbox (Use Case 6).

Spotlight — Pod Sandboxing & confidential agents

This is one of the strongest things you can do with kars today and it is one field on the CRD. Some agentic workloads handle data — health records, M&A pipeline, customer PII, classified evaluations — where the "isolated namespace + hardened container" boundary is not enough. The threat model requires a separate kernel per workload and a hypervisor barrier between the agent and the host. kars wires this into AKS Pod Sandboxing.

What you write

apiVersion: kars.azure.com/v1alpha1
kind: KarsSandbox
metadata:
  name: financial-research
spec:
  isolation: confidential        # ← that's it
  runtime:
    kind: OpenClaw

What the controller actually does

  • Sets runtimeClassName: kata-vm-isolation on the pod spec (controller/src/reconciler/mod.rs:87).
  • Adds a nodeSelector for the sandbox-kata nodepool.
  • Schedules onto a katapool with workloadRuntime: KataMshvVmIsolation, vmSize: Standard_D4as_v6 (SEV-SNP capable), enableEncryptionAtHost: true (auto-provisioned by Bicep / CLI kars add --kata).
  • Preserves all the other kars hardening — read-only rootfs, drop-ALL caps, default-deny egress, kars-strict seccomp.

What you get

  • A dedicated lightweight VM per pod via AKS Pod Sandboxing — Kata Containers running on the Azure Linux container host with the Microsoft Hyper-V Hypervisor and Cloud Hypervisor VMM. Separate kernel per workload.
  • AMD SEV-SNP attestable confidential computing — memory encryption, integrity, and remote attestation primitives at the silicon level.
  • A working example you can kubectl apply at examples/confidential-agent/.

This is what unlocks the use cases that get blocked at the regulatory review: a financial-research agent that touches non-public M&A data; a clinical agent that touches patient records; a sovereign-deployment agent on isolated infrastructure. The trust boundary is no longer "the container runtime trusts the host kernel" — it is "the workload runs in its own hypervisor-protected VM and the host cannot read its memory." Everything else about the agent — the framework, the model, the policy bundle, the mesh — works exactly the same. You change one field.

On Azure Linux — today and where we're headed

A note worth surfacing because it matters for both compliance and operations:

LayerToday (v0.1.0)Direction
kars compiled binary images (controller, inference router, A2A gateway, conformance runner) mcr.microsoft.com/azurelinux/distroless/base:3.0 — distroless, no shell, no package manager Migrate to Azure Linux 4.0 distroless (mcr.microsoft.com/azurelinux-beta/distroless/{minimal,base,debug}:4.0) when AKS support reaches GA. AL4 distroless is in public preview today.
kars agent runtime images (OpenClaw, Hermes, MAF, LangGraph, Anthropic, OpenAI Agents, Pydantic-AI) mcr.microsoft.com/azurelinux/base/python:3.12 or azurelinux/base/nodejs:24 — base images, interpreter present (Python / Node) because agent runtimes are dynamically linked Track AL4 base when the interpreter-bearing variants ship; the distroless story applies only to compiled binaries.
AKS node OS osSKU: AzureLinux (Azure Linux 3.0) — the only osSKU our Bicep uses today Switch to Azure Container Linux (ACL) — GA on AKS v1.34+, immutable Flatcar-derived node OS with read-only /usr mounted under dm-verity, no package manager, sub-5-second boot, ~40 % smaller disk than Ubuntu, ~15 % higher container density. The Bicep already carries the comment // AzureContainerLinux when GA; AzureLinux (v4) as fallback.

Two separate Microsoft Linux product lines, two separate moves. Azure Container Linux (immutable, container-host) is the natural successor for kars's AKS nodes — its threat model (immutable, dm-verity-protected) aligns directly with how kars thinks about sandbox blast-radius. Azure Linux 4.0 (general-purpose, Fedora-based) is the natural successor for kars's container base images once it stabilises and AKS support lands. Neither change requires a redesign — just a base-image bump and an osSKU change. We are watching both releases closely; the operational discipline of the substrate matters as much as the agent governance running on top of it.

The honest scope statement — when kars is not the right choice

I take credibility seriously, so here is the short list of situations where I would tell you to use something else:

  • Single agent, single user, single team, no adversarial-code threat model. Use a serverless function. Save yourself the operator overhead.
  • Pure cluster-edge LLM traffic governance with no per-agent isolation requirement. Adopt agentgateway directly. It is the right tool for that job.
  • Single-framework shop with no multi-runtime requirement. If you are 100 % LangGraph and intend to stay there, you can run vanilla LangGraph on K8s and adopt AGT directly.
  • No Kubernetes substrate. If you operate on bare VMs or pure serverless, kars does not yet have a target there.

I will not try to convert those workloads. kars's purpose is the workloads that do have the multi-agent, multi-team, adversarial, multi-runtime, regulated profile — because nothing else in the ecosystem currently serves that workload end-to-end on Kubernetes with this combination of trust boundary and governance integration.

What's on the roadmap

Themes ordered roughly by what we expect to ship first. Nothing here is dated; landing depends on what production use surfaces as the next bottleneck. The full list lives in docs/roadmap.md.

  • Trust topology, end to end. Router-side TrustGraph mesh-admission gating (pre-handshake edge check, separate from KNOCK); dynamic TrustGraph projection so topology changes do not require a sandbox roll.
  • Inference policy enforcement. Aggregate token budgets (per-hour / per-day windows) metered at the router with rejectOnExceed. Today only perRequestTokens is metered; aggregate counters are accepted on the spec and surfaced in status.
  • A2A gateway hardening. Opt-in in-binary AgentCard JWS verification axum layer (the library is complete; the wiring is the gap).
  • Admission and supply chain. Cosign-on-admission ValidatingAdmissionPolicy rejecting sandboxes whose images lack a matching cosign signature.
  • Egress allowlist authority flip. Make the signed OCI allowlist artifact the only source of truth (inline allowedEndpoints becomes read-only convenience).
  • More runtimes. CrewAI as a first-class adapter; MAF (.NET) returns when AGT ships AgentMeshClient for .NET; Strands / Google ADK once their tool-loop SDKs stabilise.
  • Multi-cluster and DR. Federated mesh registry, cross-cluster TrustGraph, cross-cluster kars handoff, AgentMesh registry/relay disaster recovery, per-cluster token budgets.
  • Observability and certification. Reproducible App Insights workbooks under deploy/workbooks/; CNCF Kubernetes AI Conformance once the upstream programme publishes.

Come build with us

The codebase is at github.com/Azure/kars, MIT-licensed. Start with the getting-started guide, then the architecture doc, then use cases. The feature maturity page is the single source of truth for what is enforced today vs reconciler-only vs library-only vs roadmap.

What we will not accept in contributions:

  • Changes that put Azure credentials into the agent process.
  • Changes that move the inference router out of the pod.
  • Changes that introduce a broker into the inter-agent encryption trust set.
  • Duplicates of AGT primitives we can invoke instead — see AGT Boundary §4.
  • Mocks, stubs, or TODO placeholders in production code.

Those constraints are the moat. Everything else is open.

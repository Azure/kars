Introducing kars — the Agent Reference Stack for Kubernetes

By Pal Lakatos-Toth · Maintainer, kars launchenterprisesecuritykubernetesai-agents

Today I'm publicly introducing kars — a Kubernetes-native runtime for AI agents that takes the position that running agents in an enterprise is fundamentally different from running stateless microservices, and that the existing stack does not yet reflect that. kars is open source, runs on any conformant Kubernetes cluster, integrates natively with the Microsoft Agent Governance Toolkit, and is designed to compose with — not replace — the SIG agent-sandbox sandboxing primitives and the Istio agentgateway data plane.

TL;DR

  • What: a Kubernetes operator + per-agent inference router + E2E-encrypted inter-agent mesh that lets you run AI agents from any framework with one consistent security, cost, and governance posture.
  • Why now: Gartner predicts 40 % of agentic-AI projects will be cancelled by end of 2027; Forrester reports 88 % of agentic-AI pilots fail to reach production. The dominant failure mode is not model quality — it's governance, cost, and security blast-radius.
  • Position: per-pod, kernel-confined trust boundary around every agent — not a centralised gateway. Default-deny egress. Zero credentials in the agent process. Cryptographic, not network-only, inter-agent trust.
  • Composes with: AGT for governance primitives, SIG agent-sandbox for the K8s primitive shape, Istio agentgateway for cluster-edge LLM traffic, your existing Foundry / Bedrock / Vertex deployments unchanged.
  • Honest scope: if you have one agent, one team, and no adversarial-code threat model, kars is overkill. The crossover is around five agents, two teams, or a regulator who has heard "prompt injection" before.
  • Source & docs: github.com/Azure/kars — Apache 2.0, contributions welcome.

The architecture in one picture

The seven outcomes kars is built to deliver

The roadmap is not a feature list. It is seven measurable customer outcomes, each tied to a documented enterprise adoption blocker. We will only ship items that demonstrably move one of these:

① Thirty-minute adoption with an operator-grade audit trail. kars up on any conformant cluster, ≤ 30 minutes from kubectl get nodes to a running governed agent, with the entire posture (policy bundle, image digest, identity, network policy) cryptographically attested and exportable.
② Per-agent autonomy tiers, not uniform governance. Gartner's documented failure pattern is that organisations apply the same control plane to a customer-facing agent, a research agent, and a SRE remediation agent. kars sets autonomy at sandbox granularity — autonomous, supervised, gated, dry-run — backed by AGT privilege rings.
③ Multi-team cost and governance separation without a separate cluster. Per-sandbox token budgets, per-team cost attribution, per-project policy bundles. Two teams can share a cluster and a model deployment without sharing a blast radius or a budget.
④ Cross-runtime and cross-organisation agent collaboration. OpenClaw, Hermes, MAF, LangGraph, CrewAI agents talk to each other on the same E2E-encrypted mesh. Federated handshake to peer organisations is on the roadmap. No central broker holds plaintext.
⑤ Behavioural observability with automated remediation. Every tool call, model call, mesh message, and policy decision is observable in Prometheus / OTel-native shape. AGT circuit breakers and the KarsKillSwitch CRD provide automated, audited remediation — not just a dashboard.
⑥ Developers spin up purposeful agents without becoming kars experts. kars up --purpose research --autonomy supervised --model gpt-4o. The CLI infers the right tool, model, and policy preset from intent. Engineers should not need a 200-page guide to ship a governed agent.
⑦ A defensible long-term bet. Open source under Apache 2.0. v1 API stability target Q4 2026. Roadmap to CNCF for upstream alignment. Designed to remain useful even if every model, framework, and gateway in the picture changes underneath it.

Why I built this — five things I think the industry has gotten wrong

I have spent the last year talking to enterprise platform teams, CISOs, and AI leads about what is actually blocking agentic deployments. Five patterns came up repeatedly. Each one is an assumption kars rejects.

1. "An agent is just a stateless microservice with an LLM in it."

It is not. An agent's code is partially generated at runtime by an untrusted source — the model output, the tool response, the previous turn's context, an MCP server you do not control. The threat model is closer to "running customer-submitted code" than to "running a service you wrote." OWASP's Agentic AI Top 10 codifies this. The implication is that the agent process must hold no secrets, must have no ambient network reach, and must be isolated at the kernel level — not just at the network policy level.

2. "One gateway can govern everything."

A cluster-edge gateway is the right place to govern callers reaching models. It is the wrong place to govern one specific agent's sub-agent spawns, its MCP tool calls, its file-system access, or its memory writes. Those happen inside the agent's process and only the agent's process knows the context. kars runs a per-pod router so that the trust boundary is where the threat is — not at the cluster edge where the threat has already escaped. We compose with agentgateway at the edge; we do not replace it.

3. "Inter-agent communication is solved by A2A."

The A2A protocol standardises agent-to-agent message shape. It does not, by itself, remove the broker from the trust set. kars uses an end-to-end Signal-Protocol encrypted mesh (X3DH + Double Ratchet) where the relay routes ciphertext and cannot read message contents. This is a structural difference, not a feature gap — the same difference as HTTPS-through-a-proxy versus PGP-encrypted email. Both are valid. They are not equivalent.

4. "Multi-runtime is a transitional problem."

I do not believe it is. The framework landscape (OpenClaw, Hermes, MAF, LangChain, LangGraph, CrewAI, OpenAI Agents SDK, Google ADK) is converging on shared standards (MCP, A2A, AGT adapters), not on a single winning framework. kars ships eight runtime adapters and treats multi-runtime as the steady state. Cross-runtime Hermes ↔ OpenClaw conversation is a production-tested guarantee, not a roadmap item.

5. "Sidecars are dead."

The Istio ambient-mode discussion has confused this point. For cluster-wide service-mesh traffic management, ambient is often the right choice. For a per-pod, kernel-confined, adversarial-trust boundary around one specific agent, a sidecar is structurally the right shape. KEP-753 made native sidecar containers a first-class K8s primitive in v1.29; this is the building block kars uses. The relevant question is not "sidecar yes/no" — it's "where does the trust boundary belong?" The answer for agent code is "as close to the agent as possible."

CIO / Engineering Leader

The business case in 90 seconds. The dominant reason agentic-AI projects fail to reach production is not model quality — it is the absence of a governance, cost, and security posture that an operator and a CISO can both sign off on. kars compresses the time-to-governable-agent from months to under a working day, on infrastructure you already operate (any conformant Kubernetes cluster). It does this by adopting open primitives — AGT for governance, SIG agent-sandbox for sandboxing shape, agentgateway at the cluster edge — and adding the small number of things that those primitives leave to the operator: a per-agent runtime, an end-to-end encrypted inter-agent channel, multi-runtime support, per-team cost attribution, and a 30-minute adoption path. The bet you are evaluating is not on kars as a vendor — it is on Kubernetes as the durable substrate for agentic workloads, the same way it became the substrate for microservices.

CISO / Security Lead

The security model in one page.

  • Zero credentials in the agent process. The agent container has no model API key, no cloud SDK token, no MCP secret. The per-pod inference router holds those, authenticates with workload identity (IMDS / projected SA token), and exposes only the call surface — never the credential. Prompt injection has nothing to exfiltrate.
  • Kernel-level egress confinement. An iptables init container restricts UID 1000 (the agent) to localhost and DNS. The agent process literally cannot open a socket to the public internet. All egress flows through UID 1001 (the router), which applies semantic policy.
  • Per-pod blast radius. One sandbox compromise contains to one Kubernetes namespace, one network policy, one set of credentials, one budget. There is no cluster-wide single point of compromise. Compare to a centralised gateway model where one compromise observes every agent's traffic.
  • End-to-end encrypted inter-agent messaging. Signal Protocol (X3DH + Double Ratchet), libsodium primitives. The relay routes ciphertext and cannot decrypt. Forward secrecy per message.
  • Cryptographic posture attestation. Image digests, policy bundles, identity, network policy — all signed and exportable. Designed to satisfy EU AI Act Article 12 logging and the Colorado AI Act evidentiary requirements through AGT's compliance proofs.
  • Coverage of the OWASP Agentic AI Top 10 at the runtime layer through AGT; the per-pod router closes the additional items that require runtime-process isolation (T01 memory poisoning, T02 tool misuse, T04 cascading hallucination, T05 unauthorized communication).
AI / Agentic AI Lead

Why this is interesting if you actually build agents. Most agentic stacks treat the agent as a single, monolithic process. Real agentic workloads spawn sub-agents, hand off tasks, call MCP tools, write to long-lived memory, and operate across organisational boundaries. kars takes each of those seriously:

  • Sub-agent spawn is governed. When an OpenClaw or MAF agent spawns a child, that child gets its own sandbox, its own policy bundle, its own autonomy tier, its own budget. Not a thread in the parent process.
  • Autonomy tiers per agent, not per cluster. Backed by AGT privilege rings (autonomous / supervised / gated / dry-run). A research agent can run autonomous; a customer-facing agent can run gated. Same cluster, same model deployment, different policy bundles.
  • AgentMesh, not just A2A. Agents from different runtimes — OpenClaw, Hermes, MAF, LangGraph — talk to each other on a shared, end-to-end-encrypted mesh. Cross-runtime conversation is production-tested with Hermes ↔ OpenClaw. The protocol is designed to extend to cross-organisation handshake.
  • Memory governance. Agent memory (Foundry Memory Store today, others on the roadmap) is bounded by per-agent policy. Writes are mediated; reads are scoped; expiry is enforceable.
  • Multi-framework adoption path. If you have invested in LangChain, MAF, or CrewAI, your existing agents run unchanged. kars adapts to your framework — you do not rewrite your agents to adopt kars.
  • SOTA-aware roadmap. The roadmap items are tagged against five evidence streams: OWASP Agentic Top 10, NIST AI RMF Agentic Profile, recent academic literature (AAGATE, MCPSHIELD), production enterprise use cases (JPMorgan's 450+ coding agents, Klarna's 853-FTE customer ops agent), and upstream landscape (AGT, agentgateway, SIG agent-sandbox).
Platform / Security Engineer

The shape on the cluster. One Helm chart installs the controller and the CRDs. kars up <name> creates a KarsSandbox CR; the controller reconciles it into a namespace, a deployment with the init container + agent container + inference-router sidecar, a default-deny NetworkPolicy, a per-agent ServiceAccount with workload identity binding, a ConfigMap with the compiled policy bundle, and a cosign-attested image reference. PodMonitor + ServiceMonitor for Prometheus, OTel spans, structured JSON logs. Compatible with Pod Security Admission "restricted", seccomp RuntimeDefault, read-only root filesystem, and confidential-VM nodes. Tested on AKS, kind, and EKS; design-compatible with GKE.

The honest scope statement — when kars is not the right choice

I take credibility seriously, so here is the short list of situations where I would tell you to use something else:

  • Single agent, single user, single team, no adversarial-code threat model. Use a serverless function. Save yourself the operator overhead.
  • Pure cluster-edge LLM traffic governance with no per-agent isolation requirement. Adopt agentgateway directly. It is the right tool for that job.
  • Single-framework shop with no multi-runtime requirement. If you are 100 % LangChain and intend to stay there, you can run vanilla LangChain on K8s and add governance with AGT directly.
  • No Kubernetes substrate. If you operate on bare VMs or pure serverless, kars does not yet have a target there.

I will not try to convert those workloads. kars's purpose is the workloads that do have the multi-agent, multi-team, adversarial, multi-runtime, regulated profile — because nothing else in the ecosystem currently serves that workload end-to-end on Kubernetes.

What's available today, and what's next

Available today (open source, Apache 2.0)

  • Kubernetes operator with KarsSandbox, KarsMemory, KarsAuthConfig, and adjacent CRDs.
  • Per-pod Rust inference router — Foundry data plane, Azure AI Content Safety, token budget, IMDS / workload-identity auth, AGT governance hooks, sub-agent spawn governance.
  • Eight runtime adapters: OpenClaw, Hermes, MAF, LangChain, LangGraph, CrewAI, OpenAI Agents SDK, Google ADK.
  • End-to-end encrypted AgentMesh — Signal Protocol, cross-runtime tested (Hermes ↔ OpenClaw bidirectional on AKS and kind).
  • 18-command CLI: kars up / add / dev / connect / handoff / mesh / ….
  • Helm chart, container images, PodMonitor / ServiceMonitor, structured logs, OTel spans.
  • Tested on AKS, kind, EKS; design-compatible with GKE.

Active roadmap (next two quarters)

  • Outcome 1 (adoption): kars doctor for posture verification, signed posture export.
  • Outcome 2 (autonomy tiers): KarsAutonomy CRD wired through to AGT privilege rings; per-tier UI affordances in the operator console.
  • Outcome 3 (multi-team): KarsProject CRD for tenant scoping, per-project token budget reconciliation, cost attribution exports.
  • Outcome 4 (cross-runtime / cross-org): A2A interop adapter, federation handshake design.
  • Outcome 5 (remediation): KarsKillSwitch CRD invoking AGT termination API, behavioural-drift detector wired to circuit breakers.

Come build with us

This is the start, not the finish. The codebase is at github.com/Azure/kars, Apache 2.0. The strategic plan, security audits, and design notes are in the docs tree. The first issue you might want to read is "Good first issues".

If you want to contribute, the work that would most directly move the seven outcomes is:

  1. Additional runtime adapters — particularly Semantic Kernel and AutoGen.
  2. A2A interop adapter (the structured handshake from AgentMesh to A2A peers).
  3. Behavioural-drift detection — pattern recognition over the mesh + tool-call telemetry.
  4. Per-agent developer ingress — chat, sessions, artifact retrieval inside the sandbox.
  5. OWASP Agentic Top 10 and NIST AI RMF mapping artifacts.
  6. GKE testing and any platform-specific deployment notes.

What we will not accept:

  • Changes that put credentials back into the agent process.
  • Changes that move the inference router out of the pod.
  • Changes that introduce a broker into the inter-agent encryption trust set.
  • Duplicates of AGT primitives we can invoke instead.
  • Mocks, stubs, or TODO placeholders in production code.

Those four constraints are the moat. Everything else is open.

If you are evaluating how to take agentic AI from pilot to production on Kubernetes, I would value the conversation. Start an issue or discussion on the repository, or reach out directly. The next 18 months of agentic AI will be decided by who solves the production governance problem — not the model quality problem. I think the answer should be open source, Kubernetes-native, and aligned with the upstream landscape. That is what kars is.

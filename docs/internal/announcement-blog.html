A thoughtful take on running AI agents on Kubernetes

By Pal Lakatos-Toth · Introducing kars, the Agent Reference Stack for Kubernetes

After many months of building, breaking, and iterating, today I want to introduce kars — the Agent Reference Stack for Kubernetes. This is not "another agent platform." It is a deliberate, opinionated position on what running AI agents in production actually requires when you have more than one team, more than one framework, and a security review board that takes "prompt injection works in practice" as a baseline assumption.

If you have one agent, one user, and one team — kars is overkill. I will say that openly. Use a serverless function and move on.

If you have five agents from two teams running against the same model deployment, with auditable per-call cost attribution, with the requirement that no agent's code can leak the cluster's model credentials, with inter-agent messaging the broker cannot read in transit, with the operational ability to govern each agent at its own autonomy tier — then read on. That is the question I built kars to answer.

What kars is

Kars is a Kubernetes operator that runs each AI agent in its own namespace, with its network egress confined by an iptables-based egress-guard and redirected through a per-pod policy enforcer (the inference router) that the agent cannot bypass — and from which the agent cannot read upstream credentials. Eleven CRDs compose into a complete governance picture: model budget, tool allow-list, memory binding, mesh trust topology, egress allowlist, eval runs. Inter-agent messaging is end-to-end encrypted using Signal Protocol via Microsoft's Agent Governance Toolkit. Eight agent frameworks (OpenClaw, Hermes, Anthropic SDK, Microsoft Agent Framework, LangGraph Python + TypeScript, Pydantic AI, OpenAI Agents) are supported via runtime adapters that all sit behind the same trust boundary.

Kars ships as a Helm chart plus a small CLI. It runs on stock Kubernetes; install is helm install. Source is at github.com/Azure/kars.

The thoughtful part

Here are the four assumptions I built kars on. If you disagree with any of them, the rest of the design will feel arbitrary. If you agree with all four, kars's specific shape will start to feel inevitable.

Assumption 1 — The agent's code is adversarial

The LLM's output is untrusted input. A tool the LLM writes a payload for may execute that payload. A sub-agent the agent spawned may be hostile. A plugin loaded at runtime may be malicious. Prompt injection works; indirect prompt injection (via tool-response content the agent treats as instruction) works. I have seen both on production agents.

The implication: don't put credentials in the agent's process. Don't trust the agent runtime to do its own egress policy enforcement; it can be tricked, patched, or replaced. Don't trust the framework to do governance; frameworks change quarterly while security primitives shouldn't. Put the trust boundary in a process the agent's user-space cannot reach. In kars this is the per-pod inference router, a separate Rust process inside the sandbox pod, running as a different UID, holding the upstream model credentials in memory the agent cannot read.

Assumption 2 — Governance applies uniformly across call types

Token budgets, content safety, tool allow-lists, model-region pinning, sub-agent spawn validation, memory store access, mesh peer admission. These are semantic policies. They depend on what the agent is asking for, and the right enforcement point is the boundary between the agent's code and the upstream surface, because that's where the policy can hold the upstream credential and observe every external action consistently. A single enforcement point gives operators one audit trail to read, one budget to manage, one allowlist to update — across model calls, tool calls, mesh messages, MCP backends, and sub-agent spawns. Six surfaces, one shape.

Assumption 3 — Inter-agent messaging benefits from end-to-end secrecy

Two agents need to talk to each other. They may live in different namespaces, clusters, or organisations. There is a broker in the middle. The conventional approach — TLS to the broker, broker forwards, TLS to the recipient — leaves the broker in the trust set: it sees every message body. That is fine when the broker is fully trusted, and increasingly hard to defend when the broker is run by a different team, a different organisation, or under cluster-admin authority you cannot prove will never be abused.

Signal Protocol (X3DH key agreement + Double Ratchet) reduces the broker to a ciphertext-routing role. The broker sees DIDs and ciphertext, nothing else. Forward secrecy is per-message. Post-compromise security restores secrecy after the attacker loses live access and a fresh DH ratchet step occurs. This is what AGT's AgentMesh provides. Kars uses upstream AGT — no kars fork. We contribute fixes back; AgentMesh stays the cross-product M365-ecosystem standard, and kars provides the Kubernetes-native enforcement and audit substrate on top.

Assumption 4 — Multi-runtime is the steady state

There is no single winning agent framework, and there will not be one. Every team has reasons for its choice: LangGraph for auditable enterprise flows, CrewAI for role-based prototyping, AutoGen for research / debate, MAF for Azure-shaped DI, OpenClaw for tool-heavy browser-grade surfaces, Hermes for stateful TUI chat. Telling teams "you must rewrite in framework X" is a non-starter. The trust boundary therefore has to be framework-agnostic. The router runs identically regardless of what's in the agent container. The governance CRDs apply identically regardless of runtime. A new framework is added by writing an adapter, not by reimplementing governance.

Kars ships eight runtime adapters in one chart today. A Hermes (Python) sub-agent and an OpenClaw (TypeScript) parent can exchange end-to-end encrypted Signal Protocol frames over the same wire format — we rebuilt the Python implementation against the TypeScript reference until both spoke identical bytes, and verified the interop end-to-end on AKS. As far as I have been able to find, no other Kubernetes agent runtime combines per-agent sandbox governance with cross-runtime Signal-Protocol inter-agent messaging.

Where I think the industry is converging — and where I deliberately deviate

Three opinions worth surfacing explicitly, because they are the parts of the design I get asked about most.

The per-pod sidecar pattern is not falling out of favor — for this problem

Istio's ambient mode replaces per-pod sidecars with per-node ztunnel proxies, and the broader Kubernetes community is rightly skeptical of historical sidecar overuse. Three things to disentangle:

  • KEP-753 made sidecars first-class in Kubernetes 1.28+. Native sidecar containers in initContainers with restartPolicy: Always exist precisely because sidecars are the right pattern for "auxiliary process whose lifecycle is bound to the workload pod." Kars uses this primitive as intended — aligned with the K8s direction-of-travel, not against it.
  • Ambient mode addresses a problem we don't have. The amortize-over-thousands-of-pods argument doesn't apply at agent-runtime scale (tens to low hundreds of agents per cluster, single-digit-MiB idle proxy).
  • Ambient mode trades per-pod isolation for per-node aggregation. A node-level proxy would hold credentials for every agent on that node — node compromise becomes a multi-tenant credential leak, and per-pod confidential-VM isolation (AMD SEV-SNP / Intel TDX) becomes incompatible with the proxy architecture. Per-pod sidecars give us single-tenant credential scope and keep the pod as the confidential-compute attestation unit. Ambient is a great answer to a different question.

AgentMesh, not "just A2A"

Google A2A is a wire protocol for cross-vendor agent discovery and message exchange, now a Linux Foundation project. It is excellent for what it solves. It does not itself provide end-to-end secrecy beyond TLS, and it is not designed for per-pair forward secrecy or KNOCK-style admission control. Kars supports A2A on the ingress side (the A2AAgent CRD declares a public endpoint terminated by our A2A gateway). For traffic between agents inside a kars trust domain, AgentMesh gives properties A2A does not: the broker is out of the trust set, forward secrecy is per-message, the recipient applies a per-message admission gate before the payload reaches the LLM. A2A is the right interop choice across trust domains; AgentMesh is the right architectural choice within. The two protocols are complementary, not substitutes.

The router as the trust boundary, not "another gateway"

The most consistent question I get is: "if I have agentgateway already, isn't the kars router redundant?" Agentgateway is excellent at what it does — a centralised AI-native data plane for LLM, MCP, and A2A traffic, with provider routing, virtual keys, and guardrails. If your problem is "I have N model deployments behind one gateway and I need traffic management and authorisation between callers and those deployments," agentgateway is the right tool.

Kars sits at a different layer. The inference router is a per-pod sidecar with cardinality one caller per router instance and a caller-is-adversarial threat model. Agentgateway is cardinality many callers per gateway with a caller-is-authenticated-client threat model. Three properties make the difference structural rather than feature-list:

  1. The agent process holds zero credentials. iptables redirects egress to the sidecar; the agent never needs an auth token of its own. There is nothing for prompt-injection to exfiltrate.
  2. Per-pod blast radius. A compromised cluster-edge gateway is a single point of compromise for every credential, every routing rule, every caller's traffic. A compromised per-pod sidecar is one sandbox.
  3. Confidential-VM compatibility. The kars router sits inside the same confidential VM as the agent; the credential mint step never leaves the encrypted memory region. A cluster-edge gateway is outside, defeating the isolation guarantee.

In a mature deployment you run both: agentgateway as the cluster-edge LLM/MCP gateway, kars per-pod as the trust boundary and agent runtime. The model call leaves the agent through the kars router (mint credentials inside the pod, enforce per-sandbox policy, decrement per-sandbox token budget), traverses the cluster network governed by Istio / mTLS, reaches a model deployment fronted by agentgateway (provider routing, load balancing, virtual keys, content-based routing), and reaches the model. Each layer does what only it can do.

Aligned with the broader ecosystem

Kars is opinionated but not in a bubble. Five upstream initiatives we explicitly align with:

InitiativeHow kars aligns
Microsoft AGT Stock upstream — no fork. AGT defines the agent-governance vocabulary (mesh transport, policy runtime, emergency-termination primitive, cryptographic compliance proofs). Kars makes those primitives K8s-CRD-shaped. We contribute fixes back.
kubernetes-sigs/agent-sandbox Overlay mode shipped (spec.upstreamCompatibility.sigsAgentSandbox: overlay). Kars-hardened SandboxTemplate on the roadmap; will be contributed upstream so any SIG-conformant SandboxClaim gets kars hardening for free.
agentgateway (Solo.io / LF) Composition story documented (see above). We make a specific point of telling customers when agentgateway alone is the right choice and kars is overkill.
OWASP Agentic Top 10 + NIST AI RMF Agentic Profile Best-in-class on ASI-05 (mesh) and ASI-07 (sandbox escape). Honest about where we are competitive vs behind; published gap analysis in the strategic plan.
Kubernetes baseline (KEP-753 sidecars, Pod Security restricted, NetworkPolicy) Standard, current K8s primitives only. The one deliberate deviation (AGT mesh instead of mTLS-via-Istio for inter-agent secrecy) is justified by the broker-trust-set argument above.

What's next

The 2026 H2 roadmap is organised by customer outcome, not by feature list. Each item answers the question "what specific customer outcome does this unblock, and what evidence says it matters?" The headline outcomes:

  1. "I can adopt kars in 30 minutes against my existing K8s cluster, and operators trust the result."
  2. "Each agent gets the right level of oversight for what it's doing." (autonomy tiers 1–5; closes the Gartner-flagged uniform-governance failure mode)
  3. "Multi-team / multi-tenant cost and governance separation with provable attribution."
  4. "Cross-runtime, cross-org agent collaboration with broker out of the trust set."
  5. "Behavioural observability + automated remediation when an agent goes off the rails."
  6. "Developers spin up the right agent without becoming kars experts." (task recipes, intake orchestrator, kars-native conversation ingress)
  7. "Kars is a defensible long-term bet." (v1 API stability, CNCF Sandbox application, named production references)

Every line item carries an evidence citation — Gartner / Forrester / Anthropic enterprise adoption surveys, OWASP / NIST / CSA security frameworks, production use-case categories. The plan is on the repository at docs/internal/2026-h2-strategic-plan.md.

Come build with us

Kars is open source under MIT, hosted at github.com/Azure/kars. Try it on your laptop: 

git clone https://github.com/Azure/kars
cd kars
make build
kars dev   # working agent inside a kind cluster in ~3 minutes

The contribution areas where we most want help — selfishly, in the order we will most enjoy reviewing the PR:

  • New runtime adapters. If your team's framework is not on the list of eight today, write the adapter. The contract is documented at docs/runtimes/CONTRACT.md; the bar is six rules.
  • Provider matrix expansion. Native router integrations for AWS Bedrock, Google Gemini / Vertex AI, Anthropic, Ollama, vLLM. Multi-cloud + on-prem coverage is one of the highest-impact gaps.
  • Guardrail integrations. Bedrock Guardrails, Google Model Armor, OpenAI Moderation, custom webhook chain. Multi-layered guardrail composition is on the roadmap.
  • SIG SandboxTemplate co-design. Co-author the kars-hardened template with us; contribute upstream to kubernetes-sigs/agent-sandbox.
  • Recipes for the task catalog. If your team has solved a particular task type well (research, security scanning, data analysis, code review), the recipe shape we ship will probably welcome yours.
  • Production-deployment case studies. Named references are how kars stops being "a Microsoft project" and starts being a community project.

What we will not accept: anything that erodes the seven irreducible advantages (per-pod trust boundary, mesh secrecy, multi-runtime adapter framework, cross-runtime mesh interop, cosign-attested compiled policy bundles, confidential-VM compatibility, Entra Agent ID integration), or that reinvents an AGT primitive instead of invoking it. The strategic plan in the repository explains why.

This is the beginning. I am looking forward to building it with you.

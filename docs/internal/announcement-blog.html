Introducing kars — the Agent Reference Stack for Azure

By Pal Lakatos-Toth launchv0.1.0open sourceMITAKS

kars is a Kubernetes-native runtime for AI agents on Azure. It treats every agent as untrusted code: per-pod kernel isolation, zero credentials in the agent process, end-to-end encrypted inter-agent mesh, and native consumption of the Microsoft Agent Governance Toolkit. v0.1.0 ships today on AKS, on the Azure Linux family, MIT-licensed.

This builds on the foundation Brendan Burns described last month — From open source to agentic systems: a hardened Azure Linux substrate (Azure Linux 4.0 + Azure Container Linux), an open agentic stack (Agent Framework, AGT, A2A), and the Agentic AI Foundation. kars is the K8s-native runtime that composes these primitives into a single, deployable stack you can drop into AKS.

TL;DR

  • What: Kubernetes operator + per-agent inference router + end-to-end encrypted inter-agent mesh, on AKS. One sandbox per agent.
  • Why: agent code is partially generated at runtime by untrusted sources (prompt injection works in practice). The trust model has to be closer to running customer-submitted code than to running a service you wrote.
  • How: consumes AGT for governance, runs on the Azure Linux family, opt-in AKS Pod Sandboxing (Kata + AMD SEV-SNP) is one CRD field. Eight first-class agent frameworks supported.
  • Try it: kars up demo --runtime openclaw — 5 min on local kind, ~15 min on a fresh AKS cluster (including provisioning).
  • Source: github.com/Azure/kars · MIT · contributions welcome.

Try it

# 1. Install the CLI (Node 22+)
npm install -g @kars/cli

# 2. Stand up your first sandbox
#    Targets local kind by default (≈ 5 min). Add --aks to provision an AKS cluster (~15 min).

# 3. Open a chat with your governed agent

Who this is for

kars is built for teams running more than one agent across more than one team, on infrastructure they already operate. Four audience tracks, with the action you should take after reading.

CIO / Engineering Leader
  • What it gives the business: a governed path from agent pilots to production on infrastructure your platform team already runs (AKS) — without standing up a separate agent stack per framework.
  • What it reuses: your existing AKS clusters, Entra ID, Azure Linux, monitoring stack, GitOps practices. No new SaaS vendor.
  • What it costs to evaluate: one pilot — one team, two agents, one regulated workflow — provides per-layer evidence for isolation, policy, and audit a CISO can sign off on.
  • The bet: on Kubernetes as the durable substrate for agentic workloads, the same way it became the substrate for microservices. kars is MIT-licensed and integrates with the Microsoft Agent Governance Toolkit; you're not buying a vendor lock-in.

CISO / Security Lead

The security model maps cleanly to the questions you actually ask:

Your questionkars's answer
Can prompt injection exfiltrate credentials?Agent process has no model API key, no cloud token, no MCP secret. The router sidecar holds them (per-sandbox Entra Agent ID via auth-sidecar in production; cluster Workload Identity in anonymous mode).
Can a compromised agent reach the internet?An iptables init container restricts UID 1000 to localhost + DNS. All egress goes through UID 1001 (router) with an L7 allowlist plus an auto-refreshing OISD + URLhaus malicious-domain blocklist.
What's the blast radius of one compromise?One namespace, one NetworkPolicy, one per-sandbox identity, one token budget. No cluster-wide single point of compromise.
Can the message broker read agent traffic?No. Signal Protocol (X3DH + Double Ratchet) end-to-end between agent processes. The AgentMesh relay routes opaque ciphertext.
How hard is the container?Read-only rootfs, drop-ALL capabilities, non-root, no privilege escalation, custom kars-strict seccomp profile (175 allowed / 41 explicit-deny syscalls), Landlock. VM-level isolation (Kata + AMD SEV-SNP) is one CRD field — see the Spotlight below.
Where's the evidence?STRIDE threat model, red-team playbook, NIST SP 800-53 + CIS Kubernetes control mapping, single-source-of-truth maturity matrix (✅ enforced vs 🟡 reconciler-only vs ⚪ roadmap).

AI / Agentic AI Lead

Real agentic workloads spawn sub-agents, hand off tasks, call MCP tools, write to memory, and federate across organisations. kars takes each of those seriously:

  • Your existing agents run unchanged. Eight first-class adapters today: OpenClaw, Hermes, OpenAI Agents (Python), Microsoft Agent Framework (Python), LangGraph (Python + TypeScript), Anthropic Claude Agent SDK, Pydantic-AI — plus a documented BYO contract. spec.runtime.kind is the only field that changes when you switch framework.
  • Sub-agent spawn is governed. When a parent agent invokes kars_spawn / kars_handoff_request, the child gets its own sandbox, its own policy bundle, its own token budget, its own AGT trust score. Not a thread in the parent process.
  • AgentMesh, not just A2A. Agents from different runtimes talk on a shared E2E-encrypted mesh today. Cross-runtime Hermes ↔ OpenClaw is exercised on kind on every push. Cross-organisation flows go through a public A2A gateway with mTLS-pinned subject (ADR 0001).
  • Per-agent policy via AGT. Hot-reloaded YAML rules gating exec / fetch / spawn / mesh-send. Different agents can run with different policy bundles on the same cluster without sharing a control plane.
  • In-cluster evaluation. KarsEval CRD replays a signed attack corpus against a sandbox and writes outcomes to the audit chain.

Spotlight — confidential agents in one CRD field

Some agentic workloads — financial research, clinical, sovereign deployments, classified evals — need more than a hardened namespace. They need a separate kernel per workload, attestable VM-level isolation, and a barrier between the agent and the host. kars wires this into AKS Pod Sandboxing.

What you write

apiVersion: kars.azure.com/v1alpha1
kind: KarsSandbox
metadata:
  name: financial-research
spec:
  runtime:
    kind: OpenClaw
  isolation: confidential   # standard | enhanced | confidential
  #          └─ confidential = Kata + AMD SEV-SNP, scheduled on Standard_DC4as_v5

What the controller does

  • Sets runtimeClassName: kata-vm-isolation on the pod spec (controller/src/reconciler/mod.rs:87).
  • Adds a nodeSelector for the sandbox-kata nodepool.
  • Schedules onto a Kata nodepool with workloadRuntime: KataMshvVmIsolation, AMD SEV-SNP capable VMs (Standard_DC4as_v5), enableEncryptionAtHost: true — auto-provisioned by Bicep or by kars add --kata.
  • Preserves all the other kars hardening (read-only rootfs, drop-ALL caps, default-deny egress, kars-strict seccomp).

What you get

  • A dedicated lightweight VM per pod via Kata Containers on the Microsoft Hyper-V Hypervisor with the Cloud Hypervisor VMM. Separate kernel per workload.
  • AMD SEV-SNP confidential computing: hardware-backed memory encryption and remote attestation, designed to protect guest memory from the host.
  • A working example at examples/confidential-agent/.

The trust boundary becomes: the workload runs in its own hypervisor-protected VM with hardware attestation; the host kernel is not in the trust set. Everything else about the agent — framework, model, policy bundle, mesh — works exactly the same. One field changes.

Why this design

Three convictions shaped kars. Each is opinionated; each rejects an assumption I see repeated in the agentic-AI conversation.

1. The agent is untrusted code, not a microservice.

An agent's instructions are partially generated at runtime by the model output, the tool response, the previous turn's context, an MCP server you do not control. The threat model is closer to running customer-submitted code than to running a service you wrote. The agent process must therefore hold no secrets, have no ambient network reach, and be isolated at the kernel — not just at the network policy.

2. Governance is the workload, not a wrapper.

Policy, audit, trust scoring, rate limiting cannot be bolted on later. The right move is to consume a real governance engine — for us that is AGT — through stable provider seams from day one. kars's AGT Boundary document says explicitly what kars never builds: no custom Signal primitives, no standalone audit chain, no parallel trust engine. Overlap is treated as a bug.

3. Inter-agent messaging needs broker-out-of-trust-set, not just A2A.

The A2A protocol standardises message shape; it does not, by itself, remove the broker from the trust set. kars uses an end-to-end Signal-Protocol encrypted mesh where the relay routes ciphertext and cannot decrypt. The structural difference is the same as HTTPS-through-a-proxy versus PGP-encrypted email. Both are valid; they are not equivalent.

The honest scope statement — when kars is not for you

I take credibility seriously. Here is the short list of situations where I would tell you to use something else:

  • Single agent, single user, single team, no adversarial-code threat model. Use a serverless function. Save yourself the operator overhead.
  • Pure cluster-edge LLM traffic governance. Adopt agentgateway directly. It's the right tool for that job; kars composes with it, not against it.
  • Single-framework shop, no multi-runtime requirement. Run your framework on K8s and adopt AGT directly.
  • No Kubernetes substrate. If you operate on bare VMs or pure serverless, kars has no target there today.

What's on the roadmap

The roadmap is organised by the customer outcome each item unblocks, not by internal theme. Every item lands against documented adoption evidence (Gartner, Forrester, Anthropic, NIST AI RMF Agentic Profile, OWASP Agentic Top 10, AAGATE). The full backlog with effort estimates and evidence trail lives in the 2026-H2 strategic plan; the highlights below.

① "I can adopt kars in 30 minutes against my existing K8s cluster"

  • Single-command install on AKS / EKS / GKE with sensible defaults — drops time-to-first-running-governed-agent below 30 min.
  • Public docs site (microsoft.github.io/kars) with copy-pastable quickstart, full CRD reference, and code-accuracy-audited architecture.
  • v1 API stability commitment + CNCF Sandbox application — unblocks enterprise procurement gates.

② "Each agent gets the right level of oversight for what it's doing"

  • Autonomy Tier 1..5 schema on KarsSandbox with per-level default policy bundles (read-only / HITL / shared / conditional / supervised). Compliance teams can sign off on Tier 1–2 without blocking Tier 4–5 review. Closes the Gartner-flagged uniform-governance failure mode.
  • Per-tier default HITL gates + a general human-in-the-loop framework (CLI + web UI) — not just for SRE actions.
  • Principled decommissioning lifecycle — revoke fed creds, deprovision Entra Agent ID, archive audit, freeze state, lock namespace.

③ "Multi-team agents against shared models, with provable cost & governance separation"

  • Native LLM providers in the router: Anthropic, AWS Bedrock, Google Gemini / Vertex, Ollama, vLLM. Breaks the Azure-only perception.
  • Native guardrails: AWS Bedrock Guardrails, Google Model Armor, OpenAI Moderation — composed into a multi-layer chain per InferencePolicy.
  • Per-team virtual keys + unified action-cost ledger spanning model + tool + MCP + mesh + spawn. One finance report.
  • SIG-aligned hardened SandboxTemplate contributed upstream — customers on the SIG primitive get the kars trust boundary via a SandboxClaim.

④ "Agents collaborate securely across runtimes, teams, organisations"

  • Mesh-aware QoS — per-peer rate limit, fair-share scheduling, KNOCK-result-aware budget.
  • Cross-runtime mesh interop with a second worked pair (MAF ↔ LangGraph) on top of the existing OpenClaw ↔ Hermes.
  • Cross-org A2A federation blueprint — two clusters, two orgs, mesh-bridged via the AGT A2A gateway.
  • Tool poisoning detection — attest MCP tool descriptions on registration; detect mid-flight drift (addresses CSA "Antigravity" / MCPSHIELD).
  • Sub-agent spawn governance hardening — TrustGraph enforcement at spawn time, delegation-chain depth caps (addresses OWASP ASI-08 cascading failures).

⑤ "Operators trust the agent fleet: behaviour stays in-bounds"

  • KarsKillSwitch CRD — label-selects sandboxes and invokes the AGT kill API. K8s-native emergency-pause surface; AGT does the actual termination.
  • Behavioural baseline + drift detection per sandbox — anomaly scoring on OTel action patterns. Closes the ASI-10 / AAGATE Behavioral Analytics gap.
  • SLO-breach → AGT-quarantine integration — kars SRE watches workload health, invokes AGT quarantine on breach.
  • Stream AGT compliance proofs into K8s Events + per-sandbox audit volume. EU AI Act + Colorado AI Act evidence at the operator surface.

⑥ "Developers spin up the right agent for the right task without becoming kars experts"

  • KarsRecipe CRD + standard catalog — research-brief, coding-task, threat-model, data-analysis, repo-scan, sre-action, chat-research. One-line task spawning with team-approved templates.
  • KarsTask CRD + CLI with per-task-kind handover patterns (PR-Draft First for coding, brief-with-citations for research, etc.).
  • Kars-native conversation ingress — talk to your running agent from a browser without kubectl port-forward.
  • Web UI — task feed, chat thread, recipe browser, sub-agent task tree, HITL inbox (Headlamp plugin + standalone kars-ui).
  • KarsArtifact CRD + KarsProject brain — typed artifact bundling and cross-task project memory with mesh-distributed append.
  • Regret-free undo — per-action undoability + auto-escalate Tier-4 tasks past 5 irreversible actions.

⑦ "Kars is a defensible long-term bet, not a Microsoft-Azure-only science project"

  • v1 API stability + deprecation policy + CRD conversion-webhook strategy.
  • CNCF Sandbox application post-v1 — independent ecosystem signal.
  • Recruit ≥3 non-Microsoft contributors in 6 months. Targets: AGT contributors at other orgs, agent-sandbox SIG, regulated-industry adopters.
  • Public benchmark publication — cold-start, router latency, mesh frame throughput, cost-per-call.
  • Production-reference customers named publicly (≥2-3 logos).

Tier sequencing

  • Tier 1 — Q3 2026 (6-8 weeks): Single-command install · docs site · Autonomy tier schema · Anthropic + Bedrock providers · KarsKillSwitch · stream AGT compliance proofs · SIG SandboxTemplate first cut.
  • Tier 2 — Q4 2026 (8-10 weeks): HITL framework · remaining LLM providers · virtual keys + cost ledger · Grafana cost dashboard · KarsRecipe/KarsTask/conversation ingress · behavioural drift detection · SIG SandboxTemplate upstream.
  • Tier 3 — Q1 2027: v1 + CNCF Sandbox · web UI · KarsArtifact/KarsProject · regret-free undo · cross-org federation · tool-poisoning detection · public benchmarks · community / customer-reference work.

Roughly 80–100 engineer-weeks across Tiers 1–3. At 2 FTE ≈ 10–12 calendar months; at 3 FTE ≈ 7–8. Tier 1 alone is what makes kars credible at the enterprise-procurement stage; everything else compounds on top.

Some invariants are non-negotiable

  • Credentials stay out of the agent process.
  • The inference router stays in the pod.
  • Inter-agent encryption remains end-to-end (the broker never enters the trust set).
  • AGT primitives are consumed, not duplicated — see AGT Boundary §4.
  • No mocks, stubs, or TODO placeholders in production code.

Everything else is open.
